# Combat reward compatibility

Reference build: `3.7.14.18`. The separately installed Lua-formula bundle has SHA-256 `dce961d2a2673c1b76b24d0579fd0120550cfbc83827418a0a37a3cc5d095f03`. Its group XP, individual XP, personal XP sharing and prospecting stages are identified by records 99, 100, 103 and 106. Formula text is read for local verification and is not included in this repository.

`CombatExperience` models the group and individual stages separately: group-level imbalance, eligible participant count, defeated monsters, bonuses and integer rounding precede the individual share, wisdom, bonuses and cap. Applying a server multiplier is a subsequent explicit local operation. It accepts zero to disable an award. Synthetic tests cover ratio boundaries, ineligible participants, living monsters, defeat, individual level caps and overflow. These mathematical tests do not by themselves prove integration with combat persistence or native result presentation.

The launcher settings retain separate decimal XP and drop multipliers, defaulting to one. Supported values range from zero to 100, with at most two decimal places. Zero disables that reward. Name and rates are saved as one JSON setting in SQLite, so a rejected update cannot change only part of the configuration. Existing server names migrate on the next successful save; the older name-only operation preserves rates. Configuration is blocked while a client is preparing or running.

Every exploration snapshot also publishes those rates to the native server-bonus model, including return from combat and reconnect. Multipliers become exact whole percentages, with no silent rounding. The current native consumer narrows the percentage fields to 16 bits; the supported launcher range keeps those fields representable. The sharing percentage remains neutral at 100. Protocol tests independently assert multiplied rates and their reappearance after combat/socket loss. The ordinary bestiary header displays catalog XP, and its item tooltips show base/prospecting chances; these labels are not evidence of the custom server reward calculation. Earned XP and generated items are verified separately in the combat result and durable inventory.

The single-player encounter calculation is integrated with the result transaction. The same transaction updates currency, XP, item stacks and the fight award; duplicate confirmations return the committed award. Reconnection restores cumulative XP and the level derived from the installed thresholds. Regular character levels currently use the configured 1–200 curve; omega progression is not projected. The native result projects current XP, its level thresholds and the combat delta, plus item prize deltas; inventory projects persistent stack identities, quantities and effects. TCP tests cover XP after socket reset, while codec tests inspect inventory and item prizes. Loot generation is connected to the current encounter and the same durable transaction. Original-client visual comparison and surface encounter population remain acceptance requirements for the complete feature. Unresolved conditions and bonus inputs must not be converted silently into successful eligibility.

The prospecting coefficient follows the pinned nonlinear formula. A configured drop multiplier scales the resulting probability, capped at 100 percent; it does not multiply a successful stack quantity. Zero disables a roll. Item effects are resolved through the installation's managed-reference registry, rather than interpreting a reference identity as an effect. Probability tests and catalog-reading tests do not establish the eligibility or frequency of generated encounter loot.

An increase in level also publishes the native level notification before the combat result. The previous level is captured when entering the encounter, before the durable award changes the selected character. This updates the live character model rather than relying on reconnect. Same-build `esf.zbb` at `0x181896bb0` consumes field 1 of `kqp` and invokes the level-state update and level-up publisher at `0x1818a5ed0`. Unchanged levels do not publish this notification, and duplicate combat acknowledgements do not repeat it.

Independent observations through the original reference-build UI provide two additional XP fixtures. In Incarnam `[-2,-3]`, a level-2 character with 5 wisdom sees 73 XP for one level-3 monster, and 262 XP for a group at levels 3, 3, 2 and 1. The implemented group and individual stages reproduce both values. These are displayed pre-combat estimates; they do not establish challenge bonuses or every possible official combat outcome.

## Loot eligibility and item generation

The runtime reads regular drops by monster grade and global drop conditions from the pinned monster bundle. Item effects and their fixed/random parameter policy come from the pinned item and effect bundles. Numeric references are resolved before rolling; variable equipment bonuses are rolled while fixed dice effects retain their ranges. One eligible successful roll adds one item for the controlled participant, subject to the source maximum. A catalog count such as 63 is not interpreted as a 63-item stack.

The native criterion factory `mt.ooz` at `0x182bc4bf0` constructs `ServerTypeCriterion` for `SC` and `SeasonCriterion` for `ST`. This was verified through decoded same-build string getters, allocation type references and constructors. `PL` maps to the level criterion, `Pm` to map, `HA` to alterations and `HS` to states. The local realm reads its game type from the installed server record and runs without a seasonal event. Character quests, alterations and combat states currently start empty; hunter capability is zero without a hunting weapon.

Conditions retain three-valued logic. An unknown fact stays unresolved, except where known values logically determine the whole expression. For example, an absent hunting capability makes `profession condition AND hunter > 0` false even when profession progress is unavailable. A fully unresolved eligibility decision fails explicitly. Variable global drop rates are also rejected if they become eligible without a resolved formula. No unknown condition is automatically admitted.

Automated checks cover all five grades of the 22 species in the six subareas intersecting the supported surface maps, using the original catalogs mounted read-only. This establishes catalog compatibility, not original per-map spawn composition or native visual acceptance. TCP tests cover a multiplied eligible drop, its rolled effect and persistent item identity after a socket reset before final acknowledgement, without duplicating the item.
