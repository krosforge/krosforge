# Combat reward compatibility

Reference build: `3.7.14.18`. The separately installed Lua-formula bundle has SHA-256 `dce961d2a2673c1b76b24d0579fd0120550cfbc83827418a0a37a3cc5d095f03`. Its group XP, individual XP, personal XP sharing and prospecting stages are identified by records 99, 100, 103 and 106. Formula text is read for local verification and is not included in this repository.

`CombatExperience` models the group and individual stages separately: group-level imbalance, eligible participant count, defeated monsters, bonuses and integer rounding precede the individual share, wisdom, bonuses and cap. Applying a server multiplier is a subsequent explicit local operation. It accepts zero to disable an award. Synthetic tests cover ratio boundaries, ineligible participants, living monsters, defeat, individual level caps and overflow. These mathematical tests do not by themselves prove integration with combat persistence or native result presentation.

The launcher settings retain separate decimal XP and drop multipliers, defaulting to one. Name and rates are saved as one JSON setting in SQLite, so a rejected update cannot change only part of the configuration. Existing server names migrate on the next successful save; the older name-only operation preserves rates. Configuration is blocked while a client is preparing or running.

The single-player encounter calculation is integrated with the result transaction. The same transaction updates currency, XP, item stacks and the fight award; duplicate confirmations return the committed award. Reconnection restores cumulative XP and the level derived from the installed thresholds. Regular character levels currently use the configured 1–200 curve; omega progression is not projected. Native result XP presentation, loot generation, inventory delivery and original-client comparison remain acceptance requirements for the complete reward feature. Unresolved conditions and bonus inputs must not be converted silently into successful eligibility.
