# Local movement and map presence

The runtime validates every cell between requested turning points against geometry read from the reference installation. The source must match the confirmed location; the path must remain within the configured length, walkable cells and the same altitude/zone region. Repeated cells, malformed segments, unsupported modes and unknown links are rejected. Facing is derived from the last traversed segment. These are explicit local exploration rules, not recovered official server scripts.

`Native/world-entry.json` declares the grid, path budget, step duration and two directed transitions. Each transition is checked against the installed map's neighbour identity, boundary column and exit flags. Arrival cells are validated against the destination geometry. Arrival choices and the interruption allowance are reconstructed local policy. Cell, neighbour and exit data come from the hash-pinned installation. The unmounted running profile uses direction-dependent segment times: 170 ms diagonally, 255 ms horizontally and 150 ms vertically on screen. These values were checked in reference build `3.7.14.18`: `xz.rle`, RVA `0x2605d50`, constructs `EntitySpeed` with float inverses of those durations (fields at offsets `0x10`, `0x14`, `0x18`; assembly SHA-256 `af866f65f0d08eebe9008ffda54462e2814d994c81059fffd766f0d685503ab3`). Mounts and other speed profiles are not covered. Other maps and transitions remain unsupported.

## Confirmation and persistence

A movement has a distinct runtime identity and a monotonic start time. An animation acknowledgement carries no movement identifier in this client protocol, so it cannot advance time or save a location. The last completed path remains available to reconcile an interruption that arrives after the timer; this window closes on acknowledgement while idle or a subsequent movement, rejection or map transition. An ACK received during a newer active movement does not clear that movement. The runtime commits the endpoint after the admitted duration. Before validating another movement, cancellation or map transition, the coordinator commits any elapsed movement under the same lock, even if its timer continuation has not run yet. Native interruption can name a reached cell or the destination of the one segment currently in progress. It cannot name a later segment or a cell outside the admitted path. When accepting that next cell, the coordinator carries its remaining travel time into the next movement; repeated cancellation cannot accumulate free steps. A path that continues beyond that cell retains the remaining time in its authoritative timeline, but is announced immediately in request order. The client predicts movement before the reply; delaying that echo can replace a newer prediction with an older destination. If the first segment retraces the interrupted edge, its duration instead covers only the distance already travelled: the client turns from its interpolated position, not from the far end of the cell. Cancelling or rejecting that shortened first segment preserves its outstanding fraction, so alternating reversals and invalid requests cannot erase travel time. A map transition also waits for that remaining time. Invalid requests stop an active movement at its reached cell instead of returning it to its original starting cell. For an accepted interruption, the moving client receives the release and observers receive the position correction. The owner already interrupted at the admitted cell: a redundant correction would reposition its interpolated animation and disturb the next prediction. Rejected requests still send a correction to every affected client, with the owner receiving its release first. A disconnect before completion discards the pending path and restores the last confirmed location on reentry.

SQLite updates compare the expected character owner and complete previous location/revision in a short transaction. A duplicate or stale operation cannot overwrite a newer revision. The in-memory confirmed location changes only after commit. Persistence failure ends the affected session; an old timer or cleanup cannot modify its replacement. No frame-by-frame database writes are needed.

A map transition requires a confirmed exit cell and no pending movement. The destination is committed before the old map receives the departure and the client receives the map load. It becomes visible in the destination only when that map is requested. Failure before commit retains the source; loss of connection after commit restores the destination.

## Ordering and isolation

One local coordinator serializes presence and location changes for the supported maps. It enqueues output without waiting for sockets. Each connection has one bounded writer, preserving frame boundaries and event order; an overflowing or stalled connection closes independently.

A map snapshot and its subsequent presence events are ordered under the same coordinator. Accounts see arrivals, movement and departures only in their current map. An account joining during a movement receives the actor's current visual cell and the remaining path; this does not commit an intermediate location. Repeated map requests do not duplicate arrival announcements.

Automated coverage includes path rejection, directional timing, monotonic completion, rapid redirection, carried travel time, cancellation spam, invalid-action recovery, stale timers, concurrent SQLite writes, failed transitions, slow output queues and two-account TCP transitions/reconnection.
